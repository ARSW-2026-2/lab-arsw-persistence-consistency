## Contexto

Un tablero colaborativo con dos servicios de negocio:

- **Gestión** (PostgreSQL): usuarios, tableros y membresías (`can_edit`). Es la autoridad de permisos.
- **Contenido y colaboración** (MongoDB + Redis): documento del tablero (`title`, `preferences`, `version`), caché de permisos para la UI y presencia efímera.

Operaciones críticas: leer el tablero, editarlo desde varios clientes, revocar permisos y mostrar quién está conectado. Restricciones de la práctica: instancias únicas (sin réplicas ni consenso), identidades simuladas por header y sin transacción compartida entre Gestión y Contenido.

La base mostró tres defectos medidos (`entrega/evidencias/base-baseline.json`):

| Defecto | Evidencia en la base |
|---|---|
| Edición perdida | Dos PUT con `expected_version=1` → `[200, 200]`, versión 1 → 3 y el título de Luis se perdió |
| Permiso revocado aceptado | Luis revocado en Gestión, permiso cacheado → PUT **200**, versión 2 |
| Presencia sin expiración | Clave presente a los 22 s |
| Redis caído | Heartbeat → **503** (`base-redis-down.json`) |
| Autoridad caída | Edición **200** usando la concesión cacheada (`base-authority-down.json`) |

## Decisión

1. **Motores.** PostgreSQL para membresías (integridad relacional y transacciones), MongoDB para el documento del tablero con preferencias embebidas (consulta por documento y atomicidad de documento), Redis para datos efímeros o derivados (presencia y caché de lectura de permisos).
2. **Frontera de atomicidad / control optimista** (`save_board`). Una sola operación `find_one_and_update({_id, version: expected}, {$set:{title}, $inc:{version:1}})`. Comparar y actualizar ocurren en la misma operación atómica de documento; si la versión ya cambió no hay coincidencia, se retorna `None` y la API responde **409**. No se usa `find` + `update`.
3. **Política de caché y garantía de escritura** (`permission_for_write`). La caché (TTL 60 s) solo responde la consulta de la UI. Toda escritura consulta a la **fuente autoritativa** (Gestión → PostgreSQL). Si Gestión no responde, el callback lanza 503 y se deja propagar: **fail-closed**, nunca se usa la concesión cacheada como respaldo. Se descartaron "acortar el TTL" (solo reduce la ventana) y "ocultar el botón" (no protege la API).
4. **Degradación** (`touch_presence`). `SET presence:{board}:{user} online EX 20` en una sola escritura; cada heartbeat renueva el TTL. Ante `RedisError` se retorna `False`: el endpoint responde 200 con `available:false` y se incrementa `lab_degraded_total{feature="presence"}`. Solo se capturan errores de Redis.

## Alternativa considerada

- **PostgreSQL + JSONB para el contenido.** `UPDATE boards SET doc = $doc, version = version + 1 WHERE id = $1 AND version = $2` da el mismo control optimista y, además, permitiría validar `memberships.can_edit` y escribir el documento **en la misma transacción** (incluso con `SELECT ... FOR SHARE` sobre la membresía), eliminando la ventana de revocación concurrente. Se descartó en esta práctica porque implica migrar el servicio de Contenido y acoplarlo a la base de Gestión, rompiendo la separación de servicios que pide el laboratorio. Queda como la opción preferida si el requisito pasa a ser "ninguna escritura después de iniciada una revocación".
- **Usar la caché para autorizar con TTL corto (p. ej., 2 s).** Más barato (sin llamada a Gestión en cada escritura), pero sigue aceptando escrituras de un usuario revocado durante el TTL y, si Gestión cae, ocultaría la falla. Descartado.
- **Eliminar Redis.** Viable (ver matriz); se conserva porque la presencia genera escrituras frecuentes de un dato sin valor histórico que no conviene llevar a las bases durables.

## Consecuencias

**Costos**

- Cada escritura hace una llamada HTTP adicional a Gestión (y una consulta a PostgreSQL). La latencia de edición aumenta y la edición depende de la disponibilidad de Gestión.
- Los usuarios verán **409** cuando editen sobre una versión vieja y deben recargar; la UI tiene que manejarlo (ya muestra el mensaje "recargue antes de editar").
- Preferencias embebidas comparten versión con el título: un cambio de preferencias concurrente con un cambio de título también produce 409.

**Fallas toleradas (degradación controlada)**

- **Redis caído:** lectura y edición siguen respondiendo 200 (la caché de lectura cae a Gestión; la escritura no usa Redis); la presencia responde 200 + `available:false`. Medido en `evidencias/09-redis-down.txt` y `solucion-redis-down.json`.

**Fallas que bloquean (deliberadamente)**

- **Gestión/PostgreSQL caído:** las ediciones responden **503** aunque exista un permiso cacheado (`solucion-authority-down.json`). La lectura del tablero sigue en 200 y la consulta de permisos para la UI sigue respondiendo desde caché mientras dure el TTL, lo cual es aceptable porque no autoriza nada.
- **MongoDB caído:** lectura y edición responden 503 (`MongoDB no disponible`); no hay copia alternativa del contenido. La presencia seguiría funcionando porque depende solo de Redis.

**Ventana entre validar permisos y escribir.** Gestión y Contenido no comparten transacción: la secuencia es (1) consultar Gestión → `can_edit=true`, (2) `find_one_and_update` en MongoDB. Si la revocación se confirma **entre** 1 y 2, esa escritura ya validada se completa. La garantía que sí damos es: *toda escritura que comienza después de que la revocación fue confirmada se rechaza con 403*. Alternativas para cerrar la ventana:

- Misma frontera transaccional (PostgreSQL + JSONB, validar y escribir en una transacción).
- **Época/versión de permisos (fencing token):** Gestión incrementa `permission_epoch` del tablero en cada revocación; Contenido guarda en el documento la época usada y la escritura se condiciona a `epoch >= actual`; o Gestión entrega un token que Contenido revalida al confirmar.
- Revalidar después de escribir y compensar (deshacer y registrar) si el permiso cambió — más complejo y deja un estado intermedio visible.

## Historial creciente

- **Almacenamiento:** colección separada `board_history` (un documento por versión): `{_id: {board: "board-1", version: 7}, board_id, version, user, title, preferences, at}`. Índice `{board_id: 1, version: -1}`.
- **Escritura:** después de un `save_board` exitoso se inserta la entrada con la versión resultante. Como `_id` incluye la versión, no hay duplicados. Para que tablero e historial no diverjan, usar una transacción multi-documento de MongoDB (requiere replica set) o el patrón outbox (registrar el evento dentro del mismo documento en una lista acotada y moverlo a historial de forma asíncrona).
- **Consulta y paginación:** por cursor, no por `skip`: `find({board_id, version: {$lt: cursor}}).sort({version: -1}).limit(20)`; el cliente envía la última versión vista. Costo estable aunque el historial crezca.
- **Retención:** política explícita (p. ej., últimas N versiones o 90 días con índice TTL sobre `at`; archivado frío para auditoría).
- **Por qué no embeberlo sin límite:** el documento crece indefinidamente (límite de 16 MB por documento en MongoDB), cada lectura del tablero —la operación más frecuente, la que medimos con k6— transportaría todo el historial, cada edición reescribiría un documento cada vez más grande y aumentaría la probabilidad de conflictos y la latencia del CAS.

**Límites que las pruebas NO demuestran:**

- No demuestran que se cierre la ventana validar→escribir ante una revocación concurrente (la prueba revoca *antes* de escribir).
- No hay réplicas: no se prueba consistencia entre réplicas, particiones de red, failover ni el teorema CAP. Detener Redis es una falla de dependencia, no una partición.
- La carga k6 es solo de lectura, 5 VU, 100 s, en una única máquina: no prueba capacidad de producción ni el costo de la llamada extra a Gestión en escrituras bajo carga, ni estabilidad de horas.
- `lab_dependency_up` y `up` solo prueban conectividad/scraping, no que las respuestas sean correctas.
