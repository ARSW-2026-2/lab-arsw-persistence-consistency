## Contexto

El sistema tiene dos servicios:

- **Gestión**, con PostgreSQL: usuarios, tableros y membresías (`can_edit`). Es quien decide si alguien puede editar.
- **Contenido y colaboración**, con MongoDB y Redis: el documento del tablero (`title`, `preferences`, `version`), una caché de permisos para la interfaz y la presencia.

Lo importante es poder leer el tablero, editarlo desde varios clientes sin perder cambios, revocar permisos y mostrar quién está conectado. Hay que tener en cuenta que todo corre en una sola instancia por motor (sin réplicas), que los usuarios se simulan con un header y que Gestión y Contenido no comparten transacciones.

Antes de tocar el código corrimos `baseline` y las pruebas de falla (`entrega/evidencias/base-*.json`) y vimos esto:

| Problema | Lo que pasó en la base |
|---|---|
| Edición perdida | Dos PUT con `expected_version=1` dieron `[200, 200]`, la versión pasó de 1 a 3 y el cambio de Luis desapareció |
| Permiso revocado aceptado | Con Luis revocado en Gestión y el permiso en caché, el PUT dio 200 y guardó |
| Presencia sin expiración | A los 22 s Ana seguía apareciendo |
| Redis caído | El heartbeat respondía 503 |
| Gestión caída | Se guardó una edición usando el permiso de la caché |

## Decisión

1. **Motores.** PostgreSQL para membresías porque necesitamos integridad y transacciones. MongoDB para el tablero, con las preferencias embebidas, porque casi siempre se lee el documento entero y la atomicidad por documento alcanza. Redis para lo que es temporal o es una copia: presencia y caché de permisos para la interfaz.
2. **Control de versiones (`save_board`).** Usamos una sola llamada `find_one_and_update` con filtro `{_id, version: expected}` que hace `$set` del título y `$inc` de la versión. Si alguien ya guardó, el filtro no encuentra nada, la función devuelve `None` y la API responde 409. No hacemos `find` y luego `update`, porque entre las dos llamadas otro cliente alcanza a escribir.
3. **Permisos para escribir (`permission_for_write`).** Siempre se le pregunta a Gestión. La caché de 60 s queda solo para que la interfaz sepa si mostrar los controles. Si Gestión no responde, se deja pasar el 503 y no se guarda nada. Es decir, ante la duda se niega. Pensamos en bajar el TTL o en esconder el botón, pero ninguna de las dos cosas impide que alguien revocado llame a la API.
4. **Presencia (`touch_presence`).** `SET presence:{board}:{user} online EX 20`, una sola escritura que pone el valor y el TTL. Cada heartbeat lo renueva. Si Redis lanza `RedisError` devolvemos `False`: el endpoint responde 200 con `available:false` y sube `lab_degraded_total{feature="presence"}`. Solo atrapamos errores de Redis para no esconder errores de programación.

## Alternativa considerada

- **PostgreSQL con JSONB para el contenido.** `UPDATE boards SET doc = $doc, version = version + 1 WHERE id = $1 AND version = $2` da el mismo control optimista. Además, se podría revisar `memberships.can_edit` y guardar en la misma transacción (por ejemplo con `SELECT ... FOR SHARE` sobre la membresía), y así se cierra la ventana de revocación que explicamos abajo. No la hicimos porque había que migrar Contenido y amarrarlo a la base de Gestión, y el laboratorio pide mantener los dos servicios separados. Si en algún momento se exige que no pase ninguna escritura después de iniciada una revocación, esta sería nuestra opción.
- **Autorizar con la caché y un TTL corto (por ejemplo 2 s).** Ahorra la llamada a Gestión, pero Luis podría seguir editando esos segundos y, si Gestión se cae, la caché taparía el problema. La descartamos.
- **Quitar Redis.** Funcionaría (lo comentamos en la matriz). Lo dejamos porque la presencia genera muchas escrituras de algo que no se necesita guardar.

## Consecuencias

**Lo que cuesta**
- Cada edición hace una llamada más a Gestión y una consulta a PostgreSQL. Editar es un poco más lento y depende de que Gestión esté arriba.
- Quien edite con una versión vieja recibe 409 y tiene que recargar. El frontend ya muestra "recargue antes de editar".
- Como las preferencias comparten versión con el título, cambiar el fondo al mismo tiempo que otro cambia el título también da 409.

**Fallas que aguantamos**
- **Redis caído:** leer y editar siguen en 200; la presencia responde 200 con `available:false`. Lo probamos en `evidencias/09-redis-down.txt`.

**Fallas que bloquean a propósito**
- **Gestión o PostgreSQL caídos:** editar da 503 aunque el permiso esté en caché (`solucion-authority-down.json`). Leer el tablero sigue funcionando, y la consulta de permisos de la interfaz sigue respondiendo desde la caché mientras dure el TTL, lo cual no es un problema porque no autoriza nada.
- **MongoDB caído:** leer y editar dan 503 porque no hay otra copia del contenido. La presencia seguiría funcionando porque solo usa Redis.

**La ventana entre validar y escribir.** Como no hay transacción compartida, una edición hace dos pasos: (1) le pregunta a Gestión y recibe `can_edit=true`; (2) guarda en MongoDB. Si la revocación se confirma justo entre el paso 1 y el 2, esa edición se guarda igual. Lo que sí garantizamos es que cualquier edición que empiece después de confirmada la revocación recibe 403. Formas de cerrar esa ventana:
- Validar y guardar en la misma transacción (la alternativa con JSONB).
- Usar una "época" de permisos: Gestión sube un contador del tablero en cada revocación, y la escritura en MongoDB lleva ese contador en el filtro para rechazar si cambió.
- Volver a revisar el permiso después de guardar y deshacer si cambió. Es más complicado y por un momento se ve un estado que no debería existir.

## Historial creciente

- **Dónde:** una colección `board_history` con un documento por versión: `{_id: {board: "board-1", version: 7}, board_id, version, user, title, preferences, at}`, con índice `{board_id: 1, version: -1}`.
- **Cómo se escribe:** después de que `save_board` funciona, se inserta la entrada con la versión nueva. El `_id` incluye la versión, así que no se repite. Para que el tablero y el historial no queden desfasados se puede usar una transacción de MongoDB (necesita replica set) o un patrón outbox.
- **Cómo se consulta:** con cursor y no con `skip`: `find({board_id, version: {$lt: cursor}}).sort({version: -1}).limit(20)`, donde el cliente manda la última versión que vio. Así cada página cuesta lo mismo aunque el historial sea enorme.
- **Cuánto se guarda:** las últimas N versiones o 90 días con índice TTL sobre `at`; lo más viejo se puede archivar.
- **Por qué no dentro del documento:** el documento crecería sin parar (MongoDB tiene tope de 16 MB), cada lectura del tablero cargaría todo el historial y cada edición reescribiría un documento cada vez más grande, lo que también hace más lentas y conflictivas las ediciones.

**Lo que las pruebas no demuestran:**
- Que la ventana entre validar y escribir esté cerrada. La prueba revoca antes de escribir, no al mismo tiempo.
- Nada sobre réplicas, particiones o CAP. Todo es de una sola instancia, y apagar Redis es una dependencia caída, no una partición.
- Capacidad real. k6 solo hizo lecturas con 5 usuarios durante 100 s en una sola máquina; no mide el costo de la llamada extra a Gestión al editar bajo carga.
- Que las respuestas sean correctas solo porque `up` o `lab_dependency_up` estén en 1. Eso solo dice que hay conexión.
